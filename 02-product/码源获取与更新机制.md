# 码源获取与更新机制（Codes Sourcing & Maintenance SOP）

- 适用站点：DragDriveCodes（全球英文流量，Google 为主）
- 适用对象：`04-site/data/codes.json` 单一数据源 + `04-site/build.py` 构建 + 三级核验分级
- 版本：v1.1，2026-11-15（v1.1 落实六项决策：Discord 每日固定动作、巡检定为每日一次、引入「官方 + 游戏内实测」快速通道、码卡举报入口、构建期断言、GSC 提交脚本）
- 标注约定：**已核实** = 本次实测或来源明确；**需核实** = 不能确认，上线前必须人工确认，不得写入站点

---

## 0. 三条前置结论（先看这里）

1. **单一官方来源不可靠。** 2026-11-15 同一天两次抓官方数据，结果不一致：游戏页显示 `BETA V1.1.9 / 更新于 9 Nov 2026 / 6.848 亿访问`，而 Roblox 公开 Games API 返回 `BETA V1.1.8 / updated 2026-09-15 / 5.797 亿访问`。说明接口与页面存在快照不同步（缓存/抓取延迟）。**结论：任何码都必须至少两条独立路径对得上，且必须比较 `updated` 时间戳后取最新。**
2. **官方每次都把新码写进游戏描述。** 两次快照的 description 都含 `NEW CODE : <CODE> +4 MORE CODES` 与 `Added 5 new Redeem Codes`。这意味着**"每 5 个码一批"是可预测的规律**，也是自动巡检最容易命中的位置。
3. **码的生命周期很短。** 现有归档里 43 个码已失效，其中 23 个是 2026 年当年的。**这个站卖的不是内容量，是"现在还能用"的时效性**，所以机制的重点是"多久发现一次变化"，而不是"写多少字"。

### 1.1.1 每日 Discord 固定动作（已拍板：每天进一次）

这是**固定动作，不是"有空再看"**。每天一次，按下面顺序走完，记录一行结论。频道名以进服后实际看到的为准（结构**需核实**，下表按常见命名给出定位方法）。

| 步骤 | 看哪里 | 具体看什么 | 判定 |
|---|---|---|---|
| 1 | 服务器公告栏 / 置顶消息（Announcements、`#announcements`、`#rules` 顶部） | 置顶的新码、当前活动、服务器级公告是否变化 | 变了 → 抄下完整字符串与日期 |
| 2 | `#announcements` 或公告类频道最近 20 条 | 新码字符串（`NEW CODE :` / `+N MORE CODES`）、版本号（`V1.x.x`）、`Next Code releasing at N Likes` | 出现码 → 走 §2.1；只出现版本号 → 走事件触发 |
| 3 | `#updates` / `#changelog` / `#patch-notes` 类频道 | 版本更新说明、维护窗口、回滚通知 | 版本变化 → 当天更新 `/updates/` |
| 4 | 码专用频道（若有，常见 `#codes` / `#redeem-codes`） | 该频道是否由管理员发布而非玩家刷屏 | 只认管理员/开发者角色发布的消息 |
| 5 | 开发者与管理员发言（按角色高亮或成员列表筛） | 延迟道歉（`sorry for delay`、`delay dikit`）、临时补偿、节日问候 | 高概率伴随新码，当天盯 |
| 6 | 服务器内搜索 | 关键词 `code`、`redeem`、`NEW CODE`、`update`、`delay`，时间限最近 24 小时 | 搜到未见过的码 → 回 A1 求证，不直接上站 |

**记录格式**（写进维护日志，一行即可）：
`2026-11-15 09:xx UTC | #announcements 20 条无新码 | #updates 无变化 | likes 209,410 | no change`
有变化时追加：`| NEW CODE <CODE> @ <频道> <消息链接或截图文件名>`。

**边界**：只做人工浏览，不抓取、不自动化登录（违反 Discord ToS，见 §4.3）；不在服务器里发言、不私信开发者。

### 1.3 独立来源的判定（很关键）

两条记录算 **1 个来源**，如果满足任一：

- 转载特征：措辞、排版、错误数值完全一致（尤其三家都写同一个可疑数字）；
- 都只有"页面级更新日期"、没有逐码日期；
- 同一运营方（同集团/同模板站群）。

**本站 Confirmed 要求：A 类官方来源 + ≥2 个彼此独立的二级来源。** 这条与 About 页现行文案一致，改规则必须同步改 About。

## 2. 核验流程

### 2.1 准入条件

| 等级 | 达成条件（满足任一即可） | 首页位置 | 卡片文案 |
|---|---|---|---|
| **Confirmed** | ① A1/A3 出现该码 **且** ≥2 个独立二级来源列为有效；② A1/A3 出现 **且** 游戏内实测通过（快速通道，见 §2.4） | 主码表 | `Confirmed` + 来源数 + `Checked <date>`；实测过的另加 `In-game tested <date>` |
| **Reported** | ① 仅 1–2 个二级来源，官方未提；② A1 只写 `+N MORE CODES` 但未给出完整字符串 | 独立区块"may still work" | `Reported` + `1 tracker only` |
| **Expired** | ① ≥2 个独立来源标过期；② 官方描述已换新批次且旧码在 A1 消失 + 1 个来源标过期；③ 实测失败 + 1 个来源标过期 | 移入 `/expired-codes/` | `Expired`，保留原奖励值 |

**`In-game tested` 是标注，不是第四级。** 它只挂在 Confirmed 上，用于表示"我们自己在游戏里换成功过"。没实测过的码**一律不加**这个标注——即使它已经被官方描述和三个追踪站确认。站内数据字段为 `codes.json` 的 `in_game_verified`（ISO 日期或 `null`）。

补充规则：
- 同一码在两个等级之间摇摆（如 `DDSSLAMETRIYADIUPDATE` 现在就是）→ **永远按低等级处理**，并在 `note` 里写清分歧。
- 奖励数额来源不一致 → 写区间（`reward_min` / `reward_max`），不取最大值，不取"看起来最爽"的数字。
- 一个新码从出现到上首页的窗口：**Reported 可以 2 小时内上，Confirmed（靠二级来源那条路径）至少等 24 小时**（给其他来源跟进的时间）；**走实测快速通道的可以当天 Confirmed**，因为证据强度更高。
- Confirmed 的码在游戏内被拒 → **当天降级**，不因为"追踪站还列着"就保留（这条已写进 About 页）。

### 2.2 失效判定与证据成本

| 方法 | 置信度 | 时间成本 | 能力边界 | 何时用 |
|---|---|---|---|---|
| 游戏内实测 | 最高 | 中：需账号、进服、1–2 分钟/码 | **每账号每码只能换一次**，测过就无法复测；小号有违规风险，不建议 | 争议码、官方首发 24h 内的关键码 |
| 官方描述换批 | 高 | 极低（读一次 A1） | 只能证明"旧批被替换"，不能证明单个码何时死 | 批量降级（最常见） |
| ≥2 独立来源标过期 | 高 | 低 | 依赖二级站更新速度，可能滞后数天 | 常规降级 |
| 玩家举报 + 截图 | 中 | 低 | 单条不可信（可能是自己换过了） | 先降到 Reported，等第二证据 |
| 单条评论/留言 | 低 | 极低 | 噪音大 | 只触发"去核验"，不直接改数据 |

### 2.3 判定流程图（文字版）

```
发现候选码
  ├─ 能否在 A1 或 A3 找到？
  │    ├─ 是 → 等 24h 看二级来源跟进数
  │    │        ├─ ≥2 个独立来源 → Confirmed
  │    │        └─ <2 个 → 先 Reported，继续观察 7 天
  │    └─ 否 → 只有社区在传
  │             ├─ ≥3 个独立来源，且能给出官方截图/链接 → Reported（note 写"官方未确认"）
  │             └─ 否则 → 不入库，仅在内部观察表记录
  └─ 已在库的码
       ├─ A1 批次已换（新码出现） → 旧码降 Expired，除非仍有 2 源列为有效
       ├─ ≥2 源标过期 → Expired
       ├─ 仅玩家举报 → 保持 Confirmed 但在 note 加"玩家报告失效（<date>），复核中"，48h 内出结论
       └─ 无法判定 → 按低等级展示，宁可少写一个码
```

### 2.4 游戏内实测证据标准（什么才算"实测通过"）

**事实边界（写文档和写文案时都不能越线）**：截至目前，站内**没有任何系统性的游戏内实测记录**——`codes.json` 里所有 `in_game_verified` 都是 `null`。因此站点文案只描述"我们如何核验"和分级定义，**不得写成"所有码都已在游戏内实测"**。一旦真的测了某个码，才把那一个日期填进去，卡片会自动多出一个蓝色 `In-game tested <date>` 徽标。

**实测通过（可填 `in_game_verified`）必须同时满足三条**：

1. 在**真实 Roblox 账号**里、于**当前版本的游戏服务器**内，把码粘贴进 `Shop → Redeem`，出现成功提示；
2. 账号 RP 余额的增加值**等于卡片上写的数额**（若卡片写的是区间，则落在区间内）；数额不符 → 先把 `reward_min` / `reward_max` 改成实测值，再写日期；
3. 记录到数据里：`in_game_verified` = 实测日期（UTC），并在 `note` 里保留原有来源说明（实测是补充证据，不删除来源）。

**不算实测通过**：

| 情况 | 为什么不算 |
|---|---|
| 提示 "invalid" / "already used" | 无法区分"码死了"和"这个账号换过"，且每账号每码只能换一次（见 §2.2） |
| 只看到别人截图 / 视频里成功 | 那是二手证据，属于"来源"，不属于实测 |
| 用小号批量试 | 有违规风险，且小号结果不能代表普通账号；不建议做 |
| 换了但没记日期 | 无法复核，等于没有证据 |
| 换了但金额与卡片不符却没改数据 | 会同时造成"金额错"和"实测记录假"两个问题 |

**成本与策略**：每账号每码只能换一次，所以实测是**一次性、不可复测**的证据，只在两种场景用——① 争议码裁决；② 官方首发 24 小时内的关键码（走 §2.1 的快速通道）。日常巡检**不做**实测。

**构建期保护**：`build.py` 的 `validate_data()` 会拒绝以下情况——`in_game_verified` 晚于 `last_verified` 或 `last_checked`、`in_game_verified` 有值但 `status` 不是 `confirmed`。也就是"实测过的码一定是 Confirmed"，反之不成立。

## 3. 更新节奏与触发条件

### 3.1 固定节奏（已拍板：每日一次）

| 频率 | 时长 | 动作 |
|---|---|---|
| **每日 1 次（固定时段，建议 09:00 UTC）** | 10–15 分钟 | ① 读 A1 描述首行；② 读 A2 的 `updated` 与 `description`，与昨日快照 diff；③ 走完 §1.1.1 的 Discord 七步；④ 看 A4 群组 shout；⑤ 抽查 1 个 active 码在二级站的投票/评论；⑥ 记一行维护日志 |
| 每月 1 日 | 15 分钟 | ① 找月度码（命名规律 `DRAGDRIVESIMULATOR<MONTH>26`）；② 更新 `last_checked`，标题月份自动跟随；③ 核对 About 页的更新承诺是否仍成立 |
| 每季度 | 1 小时 | 复核二级来源清单：哪些站已停更、哪些开始抄别人；更新 §1.2 表 |

**取消"每周一"这一档**：日常巡检只有每日一次，没有更低的常规频率。页面上的承诺必须与这里逐字对得上，对应关系如下（英文文案已落到站点，改动任一处必须同步另一处）：

| 位置 | 英文原文 |
|---|---|
| 首页 "When do new codes come out?" | `We check all three every day, and again within a few hours of any game update.` |
| About "How often this site is updated" | `Every day.` / `Within a few hours of a game update or a new code announcement.` / `Within 48 hours of a verified reader report.` |
| About 段末 | `That is the whole schedule — there is no quieter “weekly” mode.` |

> 注：48 小时是**读者举报的处理时限**，不是巡检频率；巡检本身是每日一次。两处文案都已按这个口径改写，`/contact/` 页的 "always before the next daily check" 与之同源。

### 3.2 事件触发（必须当天处理）

| 事件 | 判定信号 | 处理时限 | 动作 |
|---|---|---|---|
| 游戏版本更新 | A2 `updated` 变化 / A1 版本号变化（如 V1.1.9 → V1.2.0） | **4 小时内**（最迟 24h） | 抓新码、更新 `/updates/` 时间线与版本特性、刷新 `last_checked` |
| 官方公告出现新码字符串 | A3 公告 / A1 `NEW CODE :` 变化 | 2h 上 Reported，24h 定级 | 上首页 Reported 区块，同步跑一次核验 |
| 点赞里程碑 | A1 写 `Next Code releasing at N Likes` 且当前 likes ≥ N（当前：门槛 200,000，2026-11-11 已达 209,410） | 每 6 小时检查 | 这是"已过阈值待发"窗口，新码随时可能落地 |
| 节假日 / 本地节日 | 历史码名含 `MERDEKA`、`EIDALADHA`、`RAMADAN`、`LUNARNEWYEAR`、`ANNIVERSARY`、`INDEPENDENCE` | 提前 3 天加密到每日 2 次 | 节日码通常短命，迟一天就可能错过 |
| 官方直播 / 预告视频 | A5 新上传 / Discord 预告 | 当天 | 记录预告的码发布日期，到点蹲 |
| 延迟道歉码 | 官方写 `Sorry for delay` / `DELAYDIKIT` | 当天 | 历史出现过多次，属高概率事件 |
| 竞品站抢发 | SERP 或追踪站出现未见过的码 | 当天核验，不直接采信 | 回到 A1/A3 求证 |

### 3.3 提前发现技巧（低成本）

- **版本节奏**：现有记录显示更新集中在月末（6/28、7/31、8/29、9/27）。每月最后一周提高检查频率即可覆盖大部分更新。
- **点赞增速**：记录每日 likes，估算到下一里程碑的天数；临近阈值时改为每 6 小时。
- **描述文本 diff 优先于码 diff**：`+N MORE CODES` 这句话一变，就说明批次变了，比逐字找码更快。
- **Null 月份**：2026 年 10 月没有任何更新与月码（已核实两处来源一致），这类"空窗"要写进 `/updates/`，是差异化信息。

## 4. 自动化可行性

### 4.1 可以脚本化（低风险、只碰官方公开接口）

| 环节 | 做法 | 产出 |
|---|---|---|
| 官方快照 | 定时（≥1 小时/次，建议 6 次/天）拉 A2，存 `snapshot-YYYYMMDD-HH.json`（只存 description、updated、likes、visits） | 可 diff 的历史 |
| 变更检测 | 比较 `updated`、版本号正则 `BETA V[\d.]+`、`NEW CODE :` 后字符串、`Next Code releasing at (\d+) Likes` | 变更事件 |
| 候选码抽取 | 正则 `\b[A-Z][A-Z0-9]{7,39}\b`，再过停用词表（`RP`、`BETA`、`ROBLOX`、`DISCORD`、`UPDATE`、`NEW`、`CODE`、`DDS`、`RDID`、`LOL`…）并要求命中语义词（`MONTH` 名、`UPDATE`、`CODE`、`THX`、`DELAY`、`MERDEKA`…） | 候选清单 |
| 库内差分 | 与 `codes.json` 做集合比较，输出"新增 / 消失 / 状态可疑"三张表 | 人工待办 |
| 构建与自检 | `python build.py` + 现有静态检查（title/description/canonical/JSON-LD/死链） | 可发布产物 |
| 上线冒烟 | 部署后请求 4 个关键 URL，校验 200 / canonical / JSON-LD 可解析 | 部署报告 |
| sitemap 提交 | `04-site/scripts/gsc_submit.py`（`--check` / `--dry-run` / 直接运行），凭证只从环境变量或本地未跟踪文件读 | 收录加速；**未验证**，见 §4.4 |

### 4.2 必须人工判断

- **定级**（Confirmed / Reported / Expired）——尤其是"官方未提但社区热传"。
- **奖励数额**与区间取舍。
- **文案**：`/updates/` 时间线、各页 FAQ、About 的分级规则、版本特性描述。
- **新版本特性**摘要（不能直接抄官方描述，要重写）。
- **是否保留争议码**（如当前的 `DDSSLAMETRIYADIUPDATE`）。
- **任何需要进游戏实测的判定**。

### 4.3 抓取第三方站：可行与不可行的边界

**可以做：**

- 人工浏览，记录"事实"：码字符串、奖励、标注日期、来源链接。
- 低频（≥1 小时/次）读取公开页面标题与日期，用于判断"是否有更新"。
- 链接回原站并在文末列出 Source。

**不建议 / 不要做：**

| 行为 | 风险 |
|---|---|
| 抓取 Discord 消息（含用浏览器自动化登录后抓） | 违反 Discord ToS；账号封禁；应改用官方 bot + 权限，或人工查看 |
| 绕过 Cloudflare / 登录墙 / 验证码 | 违反站点条款，可能触犯计算机犯罪相关法规 |
| 高频轮询第三方站 | 会被 403/封 IP，且给对方造成负担；不能因为"技术能做到"就做 |
| 整段复制竞品正文或表格 | 版权风险 + AdSense 判低质/抄袭，直接毁掉变现 |
| 购买/接入第三方"码库 API" | 来源不可追溯，假码风险最高，与本站唯一卖点冲突 |
| 自动化直接发布 | 未审即上线，一个假码就毁掉信任 |
| 存储第三方站全量快照 | 只保留事实字段（码、奖励、日期、链接），不镜像内容 |

**合规底线**：遵守 `robots.txt`；带可识别 User-Agent 与联系邮箱；只取公开只读数据；Roblox 接口保持低频率（≤1 次/小时足够，不要批量扫 universe）；不碰任何需要登录的数据。

### 4.4 GSC 自动提交 sitemap：现状与前置条件（**未验证**）

脚本已写好：`04-site/scripts/gsc_submit.py`。它**没有**跑通过真实 API，原因是目前四件事都不具备——域名未注册、站点未上线、没有 GSC 属性验证、没有服务账号密钥。所以状态是「脚本可用，链路未验证」。

| 模式 | 行为 | 当前实测结果 |
|---|---|---|
| `python scripts/gsc_submit.py --check` | 只查前置条件，不发请求 | 本地构建、sitemap URL 前缀、robots 均通过；缺密钥、线上 URL 不可达 → 退出码 1 并打印 `NOT VERIFIED` |
| `--dry-run` | 打印将要发送的 PUT 请求（含 URL 编码后的 property 与 feed），不发 | 已执行，URL 形状正确 |
| 无参数 | 真的 PUT 到 Search Console API | **从未执行**（无凭证） |

**必须由你（域名上线后）完成的步骤**：

1. 注册域名、部署 `dist/`、确认 `https://<域名>/sitemap.xml` 返回 200；
2. 在 Search Console 里建属性并完成验证（DNS TXT 或 HTML 文件方式；站内目前没有 `<meta name="google-site-verification">`，走这条要改模板）；
3. 在 Google Cloud 建服务账号、下载 JSON 密钥、给项目启用 `Search Console API`；
4. 把这个服务账号邮箱**加为该 GSC 属性的用户（Full 权限）**——只在 Cloud 项目里授权无效；
5. 让脚本读到密钥：环境变量 `GSC_SERVICE_ACCOUNT_JSON`（原始 JSON 或文件路径）/ `GSC_SERVICE_ACCOUNT_FILE`，或放到 `04-site/gsc-service-account.json`（已在 `.gitignore`）。

**安全约束（已实现）**：脚本只读凭证、不回写；输出只打印 `client_email` 与 `project_id`，不打印私钥；`dist/` 与凭证文件都在 `.gitignore` 里；构建产物中不含任何密钥。

## 5. 与现有构建的对接

### 5.1 只改数据就能出页面（无需动模板）

| 变更 | 改哪里 | 自动影响 |

| 新增 / 删除码 | `codes.json` → `active` / `expired` | 首页码卡、过期表、`ItemList`、`FAQ` 中的码名列表、`/expired-codes/` 表 |

### 5.2 必须改模板（`build.py` 内字符串）

- ~~写死的数量词~~ **已修复（v1.1）**：原来的 6 处 `Five codes` / `five confirmed codes` 已全部改为 `count_word(len(ACTIVE))` 派生，FAQ 里的码名列表改为 `name_list(ACTIVE)`（自动处理 "a, b, c and d" 的顿号与 and），`A sixth code` 硬编码已删除并改为由 `UNCONFIRMED` 生成。OG 图片上的 `5 confirmed codes` 也改为派生。**现在加一个码只需要改 `codes.json`，正文与统计条同步变化。**

- `/updates/` 版本时间线（版本号、日期、特性、对应码）。

| 位置 | 现在的口径 |
|---|---|
| About「What the labels mean」 | 三级状态 + 一句"`In-game tested` 是附加标注，不是第四级" |
| About 分级表 | 新增 `In-game tested` 一行，条件是"真实账号内兑换成功、RP 增加值与卡片一致、记录日期" |
| About「What we do not do」 | 明确写 "We do not claim that every code has been tested in game" |
| 首页 callout | 说明"不做全量实测；争议码/举报码会进游戏实测并标注日期" |
| 数据层 | `in_game_verified` 全为 `null`，所以线上目前没有任何蓝色实测徽标 |

**事实边界**：站内没有系统性实测记录，文案只描述方法与分级，不写成"所有码都实测过"。改这条规则时，About 与首页必须同时改。

### 5.4 发布流程（5 步，禁止手改 `dist/`）

1. 改 `data/codes.json`（必要时 `site.json`）。
2. `python build.py`（内置数据与文案断言，见 §5.5；失败会打印原因并保留上一版 `dist/`）。
3. 跑三项目检：description 长度 120–175、canonical 正确、内链无死链。
4. 本地看两个宽度（375 / 320）首页与改动页。
5. 上传 `dist/`（Cloudflare Pages 可直接连仓库或拖拽）。

### 5.5 一致性守卫（已在 `build.py` 实现，构建失败即拦截）

`validate_data()`（在任何文件写入之前运行，失败不会破坏上一版 `dist/`）：

| # | 断言 | 失败信息示例 |
|---|---|---|
| 1 | 重复码：同一 `code` 不得跨 `active` / `unconfirmed` / `expired.*` 重复 | `X: duplicate, appears in both active and expired.2026` |
| 2 | 日期倒挂：`last_verified` / `expired_on` / `in_game_verified` 不得晚于 `site.last_checked`；`in_game_verified` 不得晚于 `last_verified` | `X: last_verified 2026-12-01 is in the future` |
| 3 | 来源数不足：`confirmed` 至少 2 个独立来源，任何条目至少 1 个 | `X: confirmed needs >=2 independent sources, has 1` |
| 4 | 数量词与统计不一致：正文出现 `Five/six/... codes are confirmed`、`the/all N confirmed codes` 而 `len(ACTIVE)` 不是该数 | `/: text says 'Five codes are confirmed' but there are 6 active codes` |
| 5 | 奖励非法：`reward_min` 必须是正整数，`reward_max >= reward_min`，且 active 总额不为 0 | `X: reward_max (20000000) is lower than reward_min (25000000)` |
| 6 | 状态与位置不一致：`active` 里必须 `status=confirmed`，`unconfirmed` 里必须 `reported`；有 `expired_on` 的不得留在 active | `X: listed as active but status is 'reported'` |
| 7 | 实测证据自洽：`in_game_verified` 有值时必须 `status=confirmed` | `X: in_game_verified is set but status is not 'confirmed'` |

`validate_copy()`：把上面第 4 条做成文本扫描，覆盖所有 8 个生成页面的 `body`，防止"改了 active 没改文案"。

验证方式（可复现）：临时往 `codes.json` 里造一条重复码 / 一条 1 来源的 confirmed / 一条日期倒挂 / 改一个数量词，`python build.py` 会以退出码 1 结束并打印 `BUILD FAILED`，恢复数据后重新构建即通过。

## 6. 出错兜底

### 6.1 SLA

| 场景 | 目标时限 | 动作 |
|---|---|---|
| Confirmed 码被证伪 / 大面积失效 | **2 小时内** | 立即降 `reported` 或 `expired`，首页移除，归档保留 |
| 奖励数额写错 | 24 小时 | 改为区间，note 注明"trackers disagree" |
| 读者举报 | 48 小时（与 About 承诺一致） | 复核 → 降级或加"复核中"备注 → 回复/不回复均可 |
| 站点级事故（构建错、页面挂） | 立即 | 回滚到上一个 `dist/` 版本 |

### 6.2 不确定性的表达（三级，全部靠 `note` + 状态实现，不改模板）

- `Confirmed`：`Checked 15 Nov 2026` + `3 independent sources`
- `Reported`：`Reported by one tracker` + `May already be expired`
- 争议中：保留 `Confirmed` 但加 `Player reports say this stopped working on <date>. Re-checking.`
- 已失效：移入归档，note 写明依据（`Marked expired by two trackers on <date>`）

**原则：不确定就说"不确定"，不要用模糊营销词（"probably works!"）掩盖。** 读者只要踩到一个假码，后面 10 个真码也不信了。

### 6.3 举报入口（已实现）

- 每张码卡底部有 `Report a problem with this code`，`mailto:` 预填主题 `Code report: <CODE>` 与正文模板（什么现象 / 平台 / 大致时间 / 补充说明）。没有表单、没有后端、没有数据库。
- 移动端可点区域：链接最小高度 44px（`.report`），与 `Copy code` 按钮同尺寸级，不挤在文字行内。
- 纯 `mailto:` 的已知边界：用户设备没配邮箱客户端时点击无反应（不报错、不跳转）。所以 `/contact/` 页仍保留完整邮箱地址作为兜底，并在该页说明举报链接已预填。
- **不做**表单/后端/数据库：会增加 GDPR 义务与维护成本，且当前不需要。若收到邮件，处理完 90 天内删除，不留个人数据。

### 6.4 月度复盘（4 个数字）

1. 本月新增码数 / 降级码数；
2. 从"被证伪"到"下架"的平均小时数（目标 ≤2h）；
3. 读者举报数与其中成立的比例；
4. 错误率 = 错码数 / 上线码数。**若 >10%，把 Confirmed 门槛从 ≥2 源提高到 ≥3 源，宁可少列。**
